> Concurrency — тема, где middle отличают от junior. Ожидается: **не просто написать, а объяснить, почему это безопасно**.

## Диагностика: что не так в этом коде?

### 1. Гонка данных

```go run
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

func main() {
	// БАГ: counter++ не атомарна
	var wg sync.WaitGroup
	counter := 0
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() { defer wg.Done(); counter++ }()
	}
	wg.Wait()
	fmt.Println("гонка, результат непредсказуем:", counter <= 1000)

	// Исправление 1: atomic
	var c1 atomic.Int64
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go func() { defer wg.Done(); c1.Add(1) }()
	}
	wg.Wait()
	fmt.Println("atomic:", c1.Load())

	// Исправление 2: каждый пишет в свой слот и суммируем потом
	parts := make([]int, 8)
	for g := range parts {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for i := 0; i < 125; i++ {
				parts[g]++
			}
		}()
	}
	wg.Wait()
	sum := 0
	for _, p := range parts {
		sum += p
	}
	fmt.Println("шардирование:", sum)
}
```

Как доказать, что гонка есть: `go run -race`, `go test -race`. Чем чинить: мьютекс (общее состояние), atomic (счётчик/флаг), канал (передача владения), «каждый — в свой слот».

### 2. Утечка горутины

```go run
package main

import (
	"fmt"
	"runtime"
	"time"
)

// БАГ: если победитель найден, остальные горутины навсегда блокируются на отправке
func firstLeaky(fs ...func() int) int {
	ch := make(chan int)
	for _, f := range fs {
		go func() { ch <- f() }()
	}
	return <-ch
}

// Исправление: буфер на число отправителей
func first(fs ...func() int) int {
	ch := make(chan int, len(fs))
	for _, f := range fs {
		go func() { ch <- f() }()
	}
	return <-ch
}

func slow(ms int) func() int { return func() int { time.Sleep(time.Duration(ms) * time.Millisecond); return ms } }

func main() {
	base := runtime.NumGoroutine()
	firstLeaky(slow(10), slow(20), slow(30))
	time.Sleep(100 * time.Millisecond)
	fmt.Println("утекло горутин:", runtime.NumGoroutine()-base)

	base = runtime.NumGoroutine()
	first(slow(10), slow(20), slow(30))
	time.Sleep(100 * time.Millisecond)
	fmt.Println("после исправления:", runtime.NumGoroutine()-base)
}
```

### 3. Deadlock

Типичные причины: двойной `Lock` одной горутиной; захват двух мьютексов в разном порядке; отправка в канал без получателя; `wg.Wait()` без `Done`; забытый `close` и `range` по каналу. Runtime сообщает `all goroutines are asleep` только когда зависли **все** горутины; частичный deadlock остаётся тихим — ловят таймаутами, `pprof goroutine` и `SIGQUIT`-дампом.

Правило против взаимной блокировки: **единый порядок захвата** ресурсов (например, по возрастанию номера) — так решается задача об обедающих философах.

## Типовые задачи на собеседовании

1. **Ping-pong**: две горутины поочерёдно печатают «ping»/«pong» (передача «хода» через каналы).
2. **Печать по порядку**: три горутины печатают 1,2,3 строго по порядку (каналы-«эстафета» или `sync.Cond`).
3. **Worker pool** с ограничением параллелизма и сбором результатов в порядке входа.
4. **Рассылка (fan-out/fan-in)**: объединить результаты нескольких источников, остановиться при первой ошибке.
5. **Потокобезопасный кэш** с TTL, LRU или singleflight.
6. **Rate limiter**: token bucket на `time.Ticker` либо по времени.
7. **Остановка горутин по сигналу**: `context`, `done` канал.
8. **Генератор простых чисел/конвейер** на каналах.
9. **Синхронизация старта**: «запустить N горутин одновременно» (канал-барьер, закрытие канала как broadcast).
10. **Реализовать `sync.WaitGroup`/семафор/блокирующую очередь** на каналах или `sync.Cond`.

Многие из них ты уже решал в неделе 3 и в заданиях. Сегодня — ещё три: ping-pong, обедающие философы и исправление утечки.

## Теория, которую спрашивают

**Почему закрывает канал отправитель?** Закрытие — сообщение «данных больше не будет»; отправка в закрытый канал вызывает panic, поэтому закрывать должен тот, кто знает, что отправок больше нет.

**Mutex или channel?** Канал — для передачи данных/владения и координации; мьютекс — для защиты общего состояния. «Не копируй мьютекс», держи секцию короткой.

**Что такое race condition и data race?** Data race — одновременный доступ к памяти без синхронизации (хотя бы одна запись) — UB; race condition — логическая зависимость результата от порядка событий (может быть и без data race).

**Что быстрее — atomic или mutex?** Atomic — на простых операциях, без блокировок; но защищает только одну переменную. Мьютекс — для инвариантов из нескольких полей.

**sync.Map vs map+Mutex?** sync.Map выгодна при «записал один раз — читают многие» и при непересекающихся ключах; иначе map+RWMutex проще и часто быстрее.

**Что такое горутина vs поток?** Лёгкая корутина планировщика Go (стек ~2 КБ растущий, переключение в пользовательском пространстве); мультиплексируется на потоки ОС.

**Как работает GOMAXPROCS?** Число P (логических процессоров); ограничивает параллельное исполнение Go-кода.

**Как остановить горутину?** Нельзя «убить» снаружи — нужно кооперативно: сигнал по каналу/контексту, который она проверяет.

**Что выведет `for i := 0; i < 3; i++ { go fmt.Println(i) }` без ожидания?** Возможно ничего: `main` завершится раньше горутин; порядок вывода не гарантирован.

**Как избежать утечки горутин при таймауте?** Буферизованный канал результата, `context`, закрытие `done`.

**Что такое memory model?** Правила, определяющие, когда запись в одной горутине гарантированно видна другой (happens-before через каналы, мьютексы, `Once`, atomic).

## Чек-лист ревью конкурентного кода

- У каждой горутины есть **владелец и условие остановки**.
- Общие данные защищены **одним** способом (не «чуть-чуть мьютекс, чуть-чуть atomic»).
- Нет блокирующих операций под мьютексом (I/O, вызовы чужого кода, отправка в канал).
- Каналы закрывает один владелец; буфер — осознанно.
- `ctx` принимается и уважается во всех блокирующих местах.
- Паники в горутинах обработаны.
- Тесты с `-race` и повторами (`-count`).
- Нет копирования структур с мьютексами; нет захвата изменяемых переменных замыканиями «по недосмотру».

## Проверь себя

<details><summary>Как создать «барьер», чтобы N горутин стартовали одновременно?</summary>Все ждут на <code>&lt;-start</code>; когда готовы, делаем <code>close(start)</code> — закрытие будит всех (broadcast).</details>

<details><summary>Как решить задачу философов без deadlock?</summary>Единый порядок захвата вилок (сначала меньший номер), либо ограничить число обедающих до N-1 семафором, либо арбитр.</details>

<details><summary>В чём разница data race и race condition?</summary>Data race — небезопасный доступ к памяти (UB, ловится <code>-race</code>); race condition — недетерминированность результата из-за порядка событий (может быть даже при корректной синхронизации).</details>
