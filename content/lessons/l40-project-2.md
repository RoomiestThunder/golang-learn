## Доводка проекта

После ядра (день 4) добавь «взрослые» свойства. Выбери то, что успеешь; обязательно — пункты 1–3.

1. **TTL для ссылок**: поле `expires_at`; `Resolve` возвращает `ErrExpired` (HTTP `410 Gone`); фоновая очистка раз в минуту (горутина с `time.Ticker`, останавливается по `context`). Это тренирует всё из недели 3.
2. **Rate limiting**: middleware на token bucket по IP (`X-Forwarded-For` — только за доверенным прокси!). 429 с заголовком `Retry-After`.
3. **Наблюдаемость**: логирующий middleware (метод, путь, статус, длительность, request_id) на `slog`; `GET /metrics` (пакет `expvar` — встроен в stdlib: счётчики запросов, редиректов, ошибок).
4. **Персистентность**: реализуй второй `Store` — снапшот в JSON-файл (периодическая запись + загрузка при старте) либо PostgreSQL через `database/sql`. Благодаря интерфейсу сервис не изменится — это и есть проверка архитектуры.
5. **Конфигурация** из env/флагов и валидация при старте.
6. **Контейнеризация**: multi-stage Dockerfile + `docker-compose.yml` (сервис + Postgres/Redis, если используешь).
7. **CI**: GitHub Actions: `go vet`, `golangci-lint`, `go test -race -cover`, сборка образа.
8. **Нагрузочный тест**: `hey`/`vegeta`/`k6` — сколько RPS держит `GET /{code}`; профиль `pprof`; опиши результаты в README.

Структура README, которая впечатляет: проблема → примеры API (`curl`) → архитектура (схема) → дизайн-решения и компромиссы → как запустить/тестировать → результаты бенчмарков → что дальше (план масштабирования: Redis-кэш, шардирование, очередь для кликов).

## Что дальше: выход на рынок

**Резюме и портфолио**
- 2–3 проекта в GitHub с README и тестами (этот сокращатель + что-то своё: CLI, бот, API с БД). Закрепи (pin) на профиле.
- В резюме — не список технологий, а **результаты**: «спроектировал X, который выдерживает N RPS», «сократил p99 с A до B».
- Блок «Стек»: Go, PostgreSQL, Redis, Docker, Kubernetes (уровень знакомства), Kafka/RabbitMQ, gRPC, Prometheus/Grafana — по факту опыта.

**Подготовка (ритм на 4 недели)**
- 3 раза в неделю: 2 задачи LeetCode (разные темы) + разбор.
- 2 раза в неделю: карточки (≈ 20 в день) и system design (одна система за сессию: сокращатель, чат, лента, rate limiter, кэш).
- Раз в неделю — mock-интервью с коллегой/другом (live coding на Go + вопросы).
- Читай исходники стандартной библиотеки (`sync`, `net/http`, `context`) — это лучший учебник по идиоматичному Go.

**Что читать/смотреть дальше**
- *Effective Go* и *Go Code Review Comments* (идиомы и стиль).
- «The Go Programming Language» (Donovan, Kernighan); «Concurrency in Go» (Cox-Buday); «100 Go Mistakes and How to Avoid Them» (Teiva Harsanyi).
- Блог go.dev, доклады GopherCon, `go.dev/doc/gc-guide`, `go.dev/ref/mem` (модель памяти).
- Open source: пройди `good first issue` в проектах на Go (Prometheus, Caddy, Hugo, k9s) — реальный опыт ревью.

**Собеседования**
- Типичный процесс: скрининг с HR → техническая беседа (язык, конкурентность, БД, сеть) → live coding (задачи уровня LeetCode easy/medium или бытовая задача на Go) → system design → поведенческое интервью.
- Проси фидбек после отказов, веди таблицу вопросов, которые не смог ответить — это твой личный план обучения.
- Уровень middle — это не «знаю всё», а «могу самостоятельно довести фичу от дизайна до продакшена, объяснить компромиссы и не ломать чужое».
