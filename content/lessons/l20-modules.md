## Модули

Модуль = дерево пакетов с файлом `go.mod` в корне.

```text
module github.com/acme/shop         // путь модуля = префикс всех импортов

go 1.24                             // минимальная версия языка
toolchain go1.24.2                  // (опц.) конкретный тулчейн

require (
    github.com/google/uuid v1.6.0
    golang.org/x/sync v0.10.0
)

replace github.com/acme/lib => ../lib   // локальная подмена (разработка)
```

- `go.sum` — контрольные суммы зависимостей (коммить в git!).
- Версии — **semver** с префиксом `v`: `v1.2.3`; для major ≥ 2 путь модуля получает суффикс `/v2`.
- **MVS** (Minimal Version Selection): Go выбирает **минимальную** версию, удовлетворяющую всем требованиям (предсказуемо, без «последних» версий).
- Команды: `go mod init`, `go get pkg@v1.2.3`, `go get -u ./...` (обновить), `go mod tidy` (почистить), `go mod why pkg`, `go list -m all`, `go mod vendor`, `go mod graph`, `go work` (мультимодульные рабочие пространства).
- Кэш модулей и прокси: `GOPROXY` (по умолчанию proxy.golang.org), приватные: `GOPRIVATE=github.com/acme/*`.
- `go install pkg@latest` ставит утилиты; в Go 1.24 в `go.mod` можно закрепить инструменты директивой `tool` и запускать `go tool <name>`.

> [!TIP] Выбирай зависимости осознанно: стандартной библиотеки хватает на многое. Чем меньше зависимостей, тем меньше обновлений безопасности и сюрпризов. Проверка уязвимостей: `govulncheck ./...`.

## Пакеты

- Имя пакета — **короткое, строчное, существительное** (`http`, `user`, `storage`), без `_` и `utils`/`common`/`helpers` (бессмысленные названия — признак плохого дизайна).
- Не повторяй имя пакета в имени идентификатора: `http.Server`, а не `http.HTTPServer`; `user.New`, а не `user.NewUser`.
- Цикличные импорты запрещены компилятором → выделяй общий пакет или инвертируй зависимость через интерфейс на стороне потребителя.
- **`internal/`**: пакеты внутри `internal` можно импортировать только из родителя этой папки (и её потомков) — компилятор запрещает внешний доступ. Используй, чтобы не раздувать публичный API.
- Экспортируй минимум. Любой публичный идентификатор — обещание обратной совместимости.

## Типичная структура сервиса

```text
shop/
├── cmd/
│   ├── api/main.go          # точка входа HTTP API (только сборка зависимостей и запуск)
│   └── worker/main.go       # другой исполняемый файл
├── internal/
│   ├── config/              # загрузка конфигурации
│   ├── domain/              # сущности и бизнес-правила (без зависимостей от БД/HTTP)
│   ├── service/             # сценарии использования
│   ├── storage/postgres/    # репозитории, SQL, миграции
│   ├── transport/http/      # обработчики, middleware, DTO
│   └── platform/            # логгер, метрики, клиенты внешних систем
├── migrations/              # SQL-миграции
├── api/                     # OpenAPI/proto
├── Dockerfile
├── Makefile
├── go.mod
└── go.sum
```

Это ориентир, а не закон (по умолчанию начинай проще — плоский `main.go` + несколько пакетов; усложняй, когда болит). `pkg/` для «публичных» библиотек сообщество использует неоднозначно — для приложения он не нужен.

Золотое правило структуры: **зависимости направлены внутрь** — домен ничего не знает про HTTP и БД; `main` собирает всё воедино (composition root).

## Инструменты качества

| Инструмент | Зачем |
|---|---|
| `gofmt` / `goimports` | Единый формат и порядок импортов (настрой на сохранение в IDE) |
| `go vet` | Типичные ошибки (форматы Printf, copylocks, lostcancel) |
| `staticcheck` | Глубокий статанализ |
| `golangci-lint` | Агрегатор линтеров (запускай в CI) |
| `go test -race` | Гонки данных |
| `govulncheck` | Известные уязвимости зависимостей |
| `dlv` (Delve) | Отладчик |
| `go generate` | Запуск генераторов кода (`//go:generate mockgen ...`, `stringer`, `sqlc`, `protoc`) |

## Сборка

```bash
go build -o bin/api ./cmd/api
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -ldflags="-s -w" -o api ./cmd/api  # кросс-компиляция, мелкий статический бинарь
go build -ldflags "-X main.version=1.2.3" ./...    # подставить версию на этапе сборки
```

Теги сборки: `//go:build integration` в начале файла + `go test -tags=integration`. Файлы с суффиксами `_linux.go`, `_windows.go`, `_amd64.go` собираются только под соответствующую платформу.

### Многоэтапный Dockerfile

```dockerfile
FROM golang:1.24 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download                 # слой с зависимостями кэшируется
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /out/api ./cmd/api

FROM gcr.io/distroless/static-debian12   # или scratch/alpine
COPY --from=build /out/api /api
USER nonroot
ENTRYPOINT ["/api"]
```

Итоговый образ — десятки мегабайт, без компилятора, с одним бинарём.

## Версионирование и совместимость

- Публичный API не ломают в рамках major-версии; ломающие изменения → `v2` (`module github.com/acme/lib/v2`).
- Следуй **Go 1 compatibility promise**: код, написанный на Go 1.x, продолжает компилироваться на новых версиях.
- Читай release notes новых версий Go: они выходят дважды в год (февраль, август), поддерживаются две последние.

## Проверь себя

<details><summary>Что хранится в go.sum и нужно ли его коммитить?</summary>Криптографические хэши версий зависимостей для проверки целостности; да, коммитить нужно.</details>

<details><summary>Что такое MVS?</summary>Minimal Version Selection: из всех требований к модулю берётся максимальная из минимальных запрошенных версий — результат воспроизводим без lock-файла.</details>

<details><summary>Зачем нужен каталог internal?</summary>Компилятор запрещает импортировать такие пакеты из-за пределов родительского дерева — скрывает детали реализации от внешних потребителей.</details>

<details><summary>Почему в Docker используют multi-stage сборку для Go?</summary>Компиляция идёт в «толстом» образе, в итоговый кладётся только статический бинарь — образ маленький и безопасный.</details>
