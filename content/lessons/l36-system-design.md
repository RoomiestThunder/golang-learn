На уровне middle на system design обычно спрашивают **небольшую** систему и смотрят на ход мысли: умеешь ли ты выяснять требования, прикидывать нагрузку, выбирать компоненты и обосновывать компромиссы.

## Каркас ответа (45 минут)

1. **Требования** (5 мин). Функциональные («сократить ссылку, перейти по ней, статистика кликов») и нефункциональные (нагрузка, задержка, доступность, согласованность, срок хранения). Явно проговори, что **не** делаешь.
2. **Оценка нагрузки** (5 мин): пользователи → запросы в секунду → объём данных → сеть.
3. **API и модель данных** (10 мин): эндпоинты, сущности, ключевые запросы, выбор хранилища.
4. **Верхнеуровневая схема** (10 мин): клиент → балансировщик → сервисы → кэш → БД → очередь/воркеры.
5. **Углубление** (10 мин): узкие места, масштабирование, отказы.
6. **Компромиссы и итоги** (5 мин): что улучшил бы, с чем сознательно согласился.

## Числа, которые стоит помнить

| Операция | Порядок |
|---|---|
| Чтение из памяти (RAM) | 100 нс |
| SSD-чтение | 100 мкс |
| Сеть внутри ДЦ (round trip) | 0.5 мс |
| Диск HDD seek | 10 мс |
| Межконтинентальный round trip | 150 мс |
| 1 млн запросов в день | ≈ 12 RPS |
| Один Go-сервис на ядро (простой API) | тысячи RPS |
| Postgres на хорошем железе | ~5–20 тыс. простых запросов/с |
| Redis | ~100 тыс. операций/с на узел |

Оценка на пальцах (URL-шортенер): 100 млн новых ссылок в месяц ≈ 40 записей/с; чтений в 100 раз больше ≈ 4000 RPS (пик ×3 ≈ 12 тыс.); 100 млн × 500 байт ≈ 50 ГБ в месяц, ~3 ТБ за 5 лет. Вывод: чтение доминирует → кэш важнее всего; хранилище — не проблема.

## Строительные блоки

- **Балансировщик** (L4/L7): nginx, Envoy, облачный LB; алгоритмы — round robin, least connections, consistent hashing.
- **Stateless сервисы** → горизонтальное масштабирование. Состояние — в БД/кэше.
- **Кэш**: Redis/Memcached, CDN для статики и публичных GET; политики вытеснения (LRU/LFU), инвалидация.
- **Базы данных**:
  - реляционные (PostgreSQL): транзакции, связи, сложные запросы; масштаб — реплики на чтение, партиционирование, шардирование;
  - NoSQL: ключ-значение (DynamoDB, Redis), документные (MongoDB), колоночные (Cassandra — запись в огромных объёмах), поисковые (Elasticsearch).
- **Очереди/стримы** (Kafka, RabbitMQ, SQS): асинхронность, сглаживание пиков, повторы, fan-out.
- **Object storage** (S3) для файлов; в БД — только ссылки.
- **Генерация ID**: автоинкремент (узкое место при шардировании), UUID (длинный, не упорядоченный), Snowflake (время + узел + счётчик), счётчики с диапазонами на воркеры.

## Масштабирование данных

- **Репликация** (лидер → фолловеры): масштабирует чтение, даёт отказоустойчивость; цена — **лаг репликации** (прочитал устаревшее). Решения: читать «свои записи» с лидера, sticky-сессии.
- **Шардирование** (горизонтальное разделение): ключ шарда выбирают так, чтобы нагрузка равномерна и запросы попадали в один шард; **consistent hashing** — минимум перемещения данных при добавлении узла; осторожно с «горячими» ключами и кросс-шардовыми транзакциями.
- **CAP**: при сетевом разделении выбираешь между согласованностью (C) и доступностью (A). **Eventual consistency**: реплики сходятся «со временем» — приемлемо для лент, счётчиков, нельзя — для денег. Идемпотентность и «saga» вместо распределённых транзакций.

## Ограничение частоты (rate limiting)

| Алгоритм | Идея | Плюсы/минусы |
|---|---|---|
| **Token bucket** | ведро пополняется со скоростью r, максимум b токенов; запрос забирает токен | допускает всплески до b; самый популярный |
| Leaky bucket | очередь с постоянной скоростью обработки | сглаживает трафик |
| Fixed window | счётчик на интервал | просто; всплеск на стыке окон (×2) |
| **Sliding window log** | хранит метки времени запросов | точно, но память O(запросов) |
| Sliding window counter | взвешенная сумма двух окон | компромисс |

Распределённый лимит — счётчик в Redis (`INCR` + `EXPIRE`, Lua-скрипт для атомарности) либо лимит на каждом узле с долей от общего. Ты реализуешь token bucket и sliding window в задании.

## Надёжность сервисов: паттерны

- **Таймауты везде** (клиент, БД, очередь) — без них один медленный сосед кладёт всю цепочку.
- **Ретраи с backoff и джиттером**, только для идемпотентных операций; бюджет ретраев, чтобы не устроить «шторм».
- **Circuit breaker**: после серии ошибок «размыкаем цепь» и быстро отказываем, давая зависимости восстановиться; затем пробный запрос (half-open).
- **Bulkhead**: отдельные пулы ресурсов для разных зависимостей — сбой одной не съедает все горутины/соединения.
- **Backpressure**: ограничивай очереди и параллелизм, отвечай 429/503 вместо бесконечного накопления.
- **Graceful degradation**: при отказе рекомендаций показываем без них.
- **Идемпотентность** (`Idempotency-Key`) и **дедупликация** на потребителях.
- **Health checks, метрики, алерты по SLO**, трассировка; деплой канарейкой.

```go run
package main

import (
	"errors"
	"fmt"
	"time"
)

// Минимальный circuit breaker
type Breaker struct {
	failures, threshold int
	openedAt            time.Time
	cooldown            time.Duration
	now                 func() time.Time
}

var ErrOpen = errors.New("цепь разомкнута")

func (b *Breaker) Call(f func() error) error {
	if b.failures >= b.threshold {
		if b.now().Sub(b.openedAt) < b.cooldown {
			return ErrOpen // быстрый отказ
		}
		// half-open: пропускаем один пробный вызов
	}
	if err := f(); err != nil {
		b.failures++
		if b.failures >= b.threshold {
			b.openedAt = b.now()
		}
		return err
	}
	b.failures = 0
	return nil
}

func main() {
	t := time.Now()
	b := &Breaker{threshold: 2, cooldown: time.Minute, now: func() time.Time { return t }}
	fail := func() error { return errors.New("db down") }
	ok := func() error { return nil }

	fmt.Println(b.Call(fail), b.Call(fail), b.Call(ok)) // третий — быстрый отказ
	t = t.Add(2 * time.Minute)                          // прошёл cooldown
	fmt.Println(b.Call(ok), b.failures)                 // пробный вызов успешен — цепь замкнулась
}
```

## Разбор: сокращатель ссылок (то, что ты построишь в проекте)

- **API**: `POST /shorten {url}` → код; `GET /{code}` → 302 редирект; опционально `GET /stats/{code}`.
- **Код**: base62 от счётчика (уникально, без коллизий, но предсказуемо) или случайные 7 символов (62⁷ ≈ 3.5·10¹² — проверка коллизий + повтор). Счётчик в распределённой системе — диапазоны, выдаваемые каждому узлу, или Snowflake.
- **Хранилище**: key-value по `code` (PostgreSQL с PK по `code` или DynamoDB/Redis); таблица `urls(code PK, url, created_at, expires_at)`; уникальный индекс по хэшу `url` для дедупликации.
- **Чтения доминируют** → Redis-кэш `code → url` (cache-aside, TTL), 302 с `Cache-Control` (301 кэшируется браузером — аналитика пропадёт).
- **Клики**: не писать в БД синхронно — класть в очередь/буфер и агрегировать батчами (или счётчики Redis).
- **Масштабирование**: stateless сервисы за LB, реплики БД на чтение, шардирование по `code`.
- **Защита**: валидация URL (схема http/https, запрет внутренних адресов — SSRF), rate limit по IP, проверка на фишинг, TTL ссылок.

## Проверь себя

<details><summary>Как оценить нагрузку на систему?</summary>От числа пользователей и действий в день к RPS (÷ 86 400, умножить на коэффициент пика), затем объём хранения и пропускная способность сети.</details>

<details><summary>Чем token bucket лучше fixed window?</summary>Допускает контролируемые всплески и не создаёт двойного трафика на границе окон.</details>

<details><summary>Что такое lag репликации и чем он опасен?</summary>Фолловер отстаёт от лидера; чтение с него может вернуть устаревшие данные («я только что сохранил, а не вижу»).</details>

<details><summary>Зачем нужен circuit breaker?</summary>Чтобы быстро отказывать при заведомо неработающей зависимости, не копить ожидающие запросы и дать ей время восстановиться.</details>
