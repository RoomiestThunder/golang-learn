## Стек и куча

- **Стек** горутины: быстрый (сдвиг указателя), автоматически освобождается при выходе из функции, не нагружает GC. Начальный размер ~2 КБ, растёт копированием.
- **Куча**: общая область для данных, живущих дольше вызова или имеющих неизвестный размер. Выделение дороже, освобождение — работа GC.

В отличие от C, **ты не выбираешь**, где разместить переменную: решает компилятор через **escape analysis** (анализ убегания).

Значение «убегает» в кучу, если компилятор не может доказать, что оно не переживёт функцию:

- возвращается указатель на локальную переменную;
- значение сохраняется в интерфейс (часто — упаковка) или передаётся в `any`-функции вроде `fmt.Println`;
- захватывается замыканием, которое живёт дольше;
- слишком большое для стека или размер неизвестен на этапе компиляции (`make([]int, n)`);
- отправляется в канал, присваивается глобальной переменной.

```go run
package main

import (
	"fmt"
	"testing"
)

type Point struct{ X, Y int }

//go:noinline
func byValue() Point { return Point{1, 2} } // остаётся на стеке

//go:noinline
func byPointer() *Point { return &Point{1, 2} } // убегает в кучу

func sink(v any) { _ = v }

func main() {
	fmt.Println("по значению: ", testing.AllocsPerRun(1000, func() { _ = byValue() }), "аллокаций")
	var keep *Point
	fmt.Println("по указателю:", testing.AllocsPerRun(1000, func() { keep = byPointer() }), "аллокаций")
	_ = keep
	fmt.Println("в interface: ", testing.AllocsPerRun(1000, func() { sink(Point{3, 4}) }) >= 0)

	// append без запаса vs с запасом
	grow := testing.AllocsPerRun(100, func() {
		var s []int
		for i := 0; i < 1000; i++ {
			s = append(s, i)
		}
	})
	pre := testing.AllocsPerRun(100, func() {
		s := make([]int, 0, 1000)
		for i := 0; i < 1000; i++ {
			s = append(s, i)
		}
	})
	fmt.Printf("append: %.0f аллокаций против %.0f с предвыделением\n", grow, pre)
}
```

Смотреть решения компилятора: `go build -gcflags="-m" ./...` (повтори `-m -m` для причин) — увидишь `escapes to heap` / `does not escape`.

**Важно:** указатель — не значит «медленно». Не гоняйся за стеком вслепую: сначала профиль. Но в горячих путях аллокации — главный враг (каждая нагружает GC).

## Как работает сборщик мусора

Go использует **конкурентный трёхцветный mark-and-sweep без перемещения и без поколений**.

1. **Mark**: от «корней» (стеки горутин, глобальные переменные, регистры) помечаем достижимые объекты. Цвета: белые (не посещены) → серые (посещены, потомки не просмотрены) → чёрные (готово). Работает **параллельно с программой**.
2. **Write barrier**: пока идёт разметка, запись указателей отслеживается, чтобы не потерять новые ссылки.
3. **Sweep**: непомеченные (белые) объекты освобождаются, память возвращается аллокатору; выполняется лениво.
4. Короткие **stop-the-world** паузы (десятки–сотни микросекунд) в начале и конце цикла.

Следствия:

- GC **нагружает CPU** (по умолчанию до ~25% ядер во время разметки) и тем сильнее, чем больше **указателей** в живых данных. Структуры без указателей (`[]int`, `[]byte`, массивы структур из чисел) GC не сканирует — они дёшевы.
- Много мелких объектов с указателями (деревья, связные списки, `map[string]*T`) — дорого. Плоские массивы значений — дёшево.
- Время паузы почти не зависит от размера кучи, а вот общий overhead — зависит.

### Настройки

- **`GOGC`** (по умолчанию 100): следующий цикл GC запускается, когда куча вырастет на 100% относительно живых данных после прошлой сборки. `GOGC=200` — реже GC, больше памяти. `GOGC=off` — отключить (опасно).
- **`GOMEMLIMIT`** (Go 1.19+, например `GOMEMLIMIT=900MiB`): мягкий лимит общей памяти процесса; GC становится агрессивнее при приближении. Комбинация «`GOGC=off` + `GOMEMLIMIT`» — приём для контейнеров с жёсткой памятью.
- Программно: `debug.SetGCPercent`, `debug.SetMemoryLimit`, `runtime.GC()`, `debug.FreeOSMemory()`.
- Диагностика: `GODEBUG=gctrace=1` печатает каждый цикл (размеры кучи, паузы, долю CPU).

```go run
package main

import (
	"fmt"
	"runtime"
)

func main() {
	var m runtime.MemStats
	runtime.ReadMemStats(&m)
	before := m.HeapAlloc

	data := make([][]byte, 0, 100)
	for i := 0; i < 100; i++ {
		data = append(data, make([]byte, 100_000)) // ~10 МБ
	}
	runtime.ReadMemStats(&m)
	fmt.Println("выросла куча:", m.HeapAlloc > before+9_000_000)

	data = nil
	runtime.GC()
	runtime.ReadMemStats(&m)
	fmt.Println("после GC освободилось:", m.HeapAlloc < before+2_000_000, "| циклов GC:", m.NumGC > 0)
}
```

## Утечки памяти в Go

GC освобождает **недостижимое**, поэтому «утечка» = объект остался достижимым, хотя не нужен:

1. **Утечки горутин** — зависшая горутина держит стек и всё, на что ссылается (самая частая).
2. Глобальные `map`/кэши, которые только растут (нет вытеснения/TTL).
3. **Слайс-подслайс** держит большой массив: `small := big[:10]` → весь `big` жив. Копируй: `slices.Clone`.
4. Строки-подстроки аналогично держат исходные данные (`strings.Clone`).
5. Незакрытые `resp.Body`, файлы, соединения, `time.Ticker`.
6. Подписки/обработчики, которые не отписываются; `context` без отмены; `defer` в бесконечном цикле.
7. Указатели в «хвосте» слайса после усечения: при `s = s[:n-1]` элемент `s[n-1]` всё ещё достижим через базовый массив — для слайсов указателей занулляй (`s[n-1] = nil`).

Как искать: рост `HeapInuse` в метриках → `pprof heap` в два момента и сравнение (`-base`), профиль `goroutine`.

## Как писать код, дружелюбный к GC

- Предвыделяй: `make([]T, 0, n)`, `make(map[K]V, n)`, `strings.Builder` + `Grow`.
- Переиспользуй буферы: `sync.Pool`, `bytes.Buffer.Reset()`.
- Избегай лишней упаковки в `interface`, `fmt.Sprintf` в горячем пути (`strconv.AppendInt`), конкатенации строк в цикле.
- Предпочитай значения указателям для мелких структур; массив структур вместо массива указателей.
- Не создавай мусор в цикле (замыкания, срезы) — выноси за цикл.
- Сначала измерь (`-benchmem`, pprof), потом оптимизируй.

## Проверь себя

<details><summary>Что такое escape analysis?</summary>Анализ компилятора, определяющий, можно ли разместить переменную на стеке или она должна жить в куче, потому что «убегает» за пределы функции.</details>

<details><summary>Какой тип GC в Go?</summary>Конкурентный, неперемещающий, непоколенческий трёхцветный mark-and-sweep с короткими stop-the-world паузами.</details>

<details><summary>Что делает GOGC=200?</summary>Следующий цикл GC начнётся, когда куча вырастет на 200% от живых данных — GC реже, памяти больше.</details>

<details><summary>Почему подслайс может вызвать утечку памяти?</summary>Он ссылается на тот же большой базовый массив; пока жив подслайс, весь массив остаётся достижимым.</details>
