Вопросы «как это устроено внутри?» — главный фильтр на собеседованиях по Go для middle. Здесь — то, что нужно знать на уровне ответа у доски.

## Планировщик: модель G-M-P

- **G** (goroutine) — горутина: стек, счётчик команд, состояние.
- **M** (machine) — поток ОС. Реально исполняет код.
- **P** (processor) — «логический процессор»: контекст выполнения с **локальной очередью** готовых горутин (до 256). Число P = `GOMAXPROCS` (по умолчанию = числу ядер).

```text
        Глобальная очередь G
                │
   ┌────────────┼────────────┐
   P0 ─ M0      P1 ─ M1      P2 ─ M2        (M привязан к P, пока выполняет Go-код)
   │ локальная   │ локальная   │ локальная
   │ очередь G   │ очередь G   │ очередь G
```

Как работает:

1. `go f()` создаёт G и кладёт в локальную очередь текущего P (следующей на запуск — `runnext`).
2. M берёт G из очереди своего P и исполняет до блокировки, завершения или вытеснения.
3. **Work stealing**: если очередь P пуста, он берёт G из глобальной очереди, сетевого поллера или **крадёт половину** очереди другого P.
4. **Блокирующий системный вызов**: M уходит в syscall вместе с G, а P **передаётся** другому M (или создаётся новый) — остальные горутины продолжают работать.
5. **Сетевой ввод-вывод** не блокирует потоки: используется **netpoller** (epoll/kqueue/IOCP). Горутина паркуется, пока сокет не готов, поток свободен для других.
6. **Вытеснение (preemption)**: с Go 1.14 — асинхронное (через сигнал): горутина, крутящаяся в цикле без вызовов функций, всё равно будет прервана (квант ≈ 10 мс).
7. Блокировка на канале/мьютексе/`time.Sleep` — это **парковка** горутины (G уходит в wait-очередь), поток не блокируется.

Следствия:

- Миллионы горутин возможны: стек стартует ~2 КБ и **растёт копированием** (при нехватке выделяется вдвое больший сегмент и содержимое переносится; указатели на стек корректируются).
- `runtime.GOMAXPROCS(n)` ограничивает параллелизм Go-кода, но не число потоков ОС (блокирующие syscalls/cgo создают дополнительные).
- Горутины **не детерминированы**: порядок выполнения не гарантирован — нельзя полагаться на «горутина стартует раньше».
- CPU-bound горутин ≫ ядер не ускорит работу; для I/O-bound — отлично.

Инструменты: `GODEBUG=schedtrace=1000 ./app`, `runtime/trace` (`go tool trace`) — визуализация планировщика.

## Каналы внутри

`chan T` — указатель на структуру `hchan`: **кольцевой буфер** (для буферизованных), счётчики, `closed`, **очереди ожидающих** отправителей (`sendq`) и получателей (`recvq`) из `sudog` и **мьютекс** (это ключевой факт: канал защищён внутренним локом, а не «магией»).

- Отправка в канал с ожидающим получателем — **прямая передача** значения в стек получателя, минуя буфер.
- Буфер полон/пуст — горутина паркуется в `sendq`/`recvq` и будится парным действием.
- `close` будит всех ожидающих (получатели получат zero value, отправители — panic).
- `select` блокирует горутину сразу на нескольких каналах (с упорядоченным по адресам захватом локов для избежания deadlock), выбор среди готовых — псевдослучайный.

## map внутри

- До Go 1.24: массив **бакетов** по 8 пар ключ/значение, хэш-функция с рандомным seed; старший байт хэша — «tophash» для быстрого пропуска; при росте load factor (≈6.5) таблица удваивается с **постепенной эвакуацией** бакетов. Переполнения — цепочки overflow-бакетов.
- Go 1.24+: **Swiss Tables** — группы по 8 слотов с контрольными байтами, SIMD-подобная проверка, лучше по скорости и памяти.
- Итерация **намеренно рандомизирована** (стартовая позиция/смещение); поэтому порядок нельзя использовать.
- **Не потокобезопасна**: runtime делает флаг «идёт запись» и аварийно падает при конкурентной записи (`fatal error`).
- Ключ должен быть сравним и хэшируем; NaN как ключ — каждый раз новый ключ (`NaN != NaN`).
- Удаление не уменьшает память; для «сброса» создай новую map.

## slice и string внутри

```go
type slice struct { ptr unsafe.Pointer; len, cap int }   // 24 байта
type string struct { ptr unsafe.Pointer; len int }        // 16 байт
```

Рост при `append` (приблизительно): до 256 элементов — ×2, дальше — плавный переход к ×1.25 (формула с `(newcap + 3*256)/4`); итог округляется до размера класса аллокатора, поэтому `cap` бывает «странным». Не полагайся на конкретные числа.

## Интерфейсы внутри

- Пустой `any` (eface): пара `(type *_type, data unsafe.Pointer)`.
- Непустой (iface): `(tab *itab, data unsafe.Pointer)`; **itab** — таблица методов для пары (интерфейс, конкретный тип), кэшируется. Вызов метода — косвенный через таблицу (чуть дороже прямого, мешает инлайнингу).
- Значение небольших типов и указателей хранится прямо в data или упаковывается в кучу (**boxing**) — отсюда аллокации при передаче в `any`.
- Отсюда ловушка `nil`-интерфейса: `(type=*T, data=nil) != nil`.

## defer, panic

- `defer` реализован «open-coded» (с Go 1.14) — почти бесплатен в большинстве случаев; в цикле — дороже (куча записей).
- `panic` раскручивает стек, выполняя отложенные вызовы; `recover` останавливает раскрутку; `os.Exit` defer не выполняет.

## Модель памяти Go (happens-before)

Корректность конкурентного кода определяется отношением **«происходит раньше»**. Основные гарантии синхронизации:

- `go` statement happens-before начала выполнения горутины.
- Отправка в канал happens-before соответствующего приёма; закрытие канала — до приёма «закрыто»; приём из небуферизованного канала — до завершения отправки.
- `mu.Unlock()` n-го вызова happens-before `mu.Lock()` n+1-го.
- `once.Do(f)`: завершение `f` happens-before возврата из любого `Do`.
- Операции `sync/atomic` — последовательно согласованы.

Без таких рёбер чтение переменной, записанной другой горутиной, **не гарантирует** увидеть значение (компилятор и CPU переупорядочивают). «Работает на моей машине» — не доказательство; `go test -race`.

## Полезные приёмы изучения

```bash
go build -gcflags="-m -m"     # решения escape analysis и инлайнинга
go tool compile -S file.go    # ассемблер
GODEBUG=gctrace=1,schedtrace=1000 ./app
go tool trace trace.out       # визуальный трейс планировщика/GC
```

## Проверь себя

<details><summary>Что такое P в модели GMP и зачем он нужен?</summary>Логический процессор с локальной очередью горутин и ресурсами (кэши аллокатора); позволяет масштабировать планировщик без глобального лока и передавать «работу» другому потоку, когда M блокируется в syscall.</details>

<details><summary>Что происходит, когда горутина блокируется на системном вызове?</summary>Её M блокируется вместе с ней, а P отсоединяется и передаётся другому (новому) M, чтобы остальные горутины продолжали выполняться.</details>

<details><summary>Почему порядок обхода map случайный?</summary>Runtime намеренно рандомизирует начальную точку итерации, чтобы разработчики не полагались на порядок (он менялся бы с реализацией).</details>

<details><summary>Как устроен канал?</summary>Структура hchan: кольцевой буфер, очереди ожидающих отправителей и получателей (sudog), флаг закрытия и мьютекс.</details>

<details><summary>Как стек горутины растёт?</summary>При нехватке места выделяется новый, обычно вдвое больший непрерывный стек, содержимое копируется, указатели корректируются; старый освобождается.</details>
